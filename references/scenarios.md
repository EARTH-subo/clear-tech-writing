# 按文本类型落地

同一套规则，不同文本类型的重点不同。先在这里找到对应的一节，再回 SKILL.md 查具体规则。

**通用前提**：先把 `代码`、命令、路径、字段名、URL、表格、公式、YAML front matter、Mermaid 全部标出来，原样保留，只改散文。这些不是句子，不套句长，不改大小写，不翻译。

## 1 任务汇报 / 排障结论（report，strict）

读者只关心三件事：到底成了没、根因是什么、哪块验过了。不看你的摸索过程。

- 首句给结论，不给铺垫。
- 状态词固定；工作状态与验证状态分开写。
- 证据写到 `路径:行号` / 提交号 / 完整命令。
- 没做的写"未做"并说明原因；缺证据的写"未确认"并写确认方法。

模板：

```
<状态词>：<完成范围与结果>。

**原因**：<有证据的根因；没有就写"原因未确认"及确认方法>
**改动**
- `路径:行号` — <改了什么>
**验证**
- 已验证：<方法与范围> — <结果>
- 未验证：<检查项> — <原因>
**未做**
- <事项> — <原因>
```

不需要的段落直接删，不要留空标题。

## 2 操作步骤 / Runbook（procedure，strict）

- 一步一个动作；同时发生的才合并。
- 前置条件单列，放在步骤之前。
- 人的动作用祈使句，系统的行为另起一句、以组件为主语。
- 危险步骤的警告放在它前面，只写危险 / 后果 / 规避。
- 预期结果写在动作之后，另起一句。

模板：

```
前置条件：
- <条件 1>
- <条件 2>

警告：<危险>。<后果>。<规避动作>

1. <动词开头，一个动作>。
   系统显示「<预期结果>」。
2. <动词开头，一个动作>。
```

## 3 错误信息（strict）

读者此刻正在失败，只需要知道：发生了什么、影响什么、下一步做什么。

- 一句说事实，一句说动作。不写"抱歉""出了点问题"。
- 保留原始错误码与技术标识，不改写、不翻译。
- 说明影响范围（哪个功能不可用、数据是否受影响）。
- 说明恢复方式或下一个可执行动作。
- 不把"可能"写成"是"。

模板：

```
<组件> <动作> 失败：<具体原因>（<错误码>）。
<影响范围>。
<下一步动作或恢复方式>。
```

## 4 工具 / 函数描述（descriptive，strict）

给模型读的，误读会导致调错参数。

- 一句话说清"做什么、对什么、返回什么"。
- 参数、类型、单位、默认值、必填与否，一项一行，不混进散文。
- 说明失败时的行为（抛错 / 返回空 / 重试）。
- 不用"强大的""灵活的""一站式"这类无信息形容词。
- 不在描述里写实现细节和营销话术。

## 5 Agent 间指令 / system prompt（strict）

- 一条指令一个句子，祈使句。
- 条件写在动作前：`如果 X，则 Y。` 不写 `Y，如果 X 的话`。
- 明确优先级：冲突时以哪条为准，写出来。
- 不用"尽量""适当""必要时"——模型无法执行没有阈值的指令。
- 禁止项写"不得 / 禁止 + 具体动作"，不写"不要随便……"。

## 6 技术问答 / FAQ（descriptive，flavored）

读者带着一个具体问题来，只想要答案。答案常被检索、被复制、被引用，所以必须**脱离上下文也能读**。

- **先答后释**：第一句就直接回答问题，不写"这个问题很常见""首先我们需要了解"。
- **一条答案自包含**：不写"如上所述""接上文""在上一节的基础上"。同类问题合并时，各自写清前提。
- **版本 / 环境前提写在最前**：答案随版本变化，先说明"适用于 2.x""仅在 Linux 下"。
- **不确定就写条件**：不写"可能是 A 也可能是 B"，写"如果 X 出现则 A，否则 B"。真查不清就写"原因未确认"和确认方法。
- **对比类问题先给结论**：先回答选哪个，再写"什么情况下反过来"。
- **给可执行的验证方式**：命令 + 预期输出，让读者自己确认，不要求他信你。
- **不写收尾寒暄**：删"希望对你有帮助""如有疑问欢迎交流"。

模板：

```
<一句直接答案>。

<前提或适用范围>

按以下顺序排查：
1. <动作>。`<命令>`
   - <结果 A>：<含义与下一步>
   - <结果 B>：<含义与下一步>
2. <动作>。

<反直觉情况或例外>
```

反例：

> 关于容器启动后立即退出的问题，其实这个情况是比较常见的，通常来说可能是由于多种原因导致的。首先我们需要了解一下容器的运行机制……

问题：铺垫三句没给答案；"比较常见""多种原因""可能"都是空信息；读者读到第五句还不知道该做什么。

## 7 README / 入口页（descriptive，flavored）

首段回答四个问题：这是什么、给谁用、解决什么、从哪开始读。

- 不要标题、正文、按钮三处重复同一句话。
- 安装步骤按第 2 节写，不要混进介绍段。
- 能力说明给可核对的事实（支持什么格式、上限多少），不给评价。

## 8 PR 描述 / changelog（descriptive，flavored）

- PR 首句写"改了什么、为什么"，不写"根据需求修改了相关代码"。
- 变更按"新增 / 修改 / 修复 / 移除"分组，一条一行。
- 兼容性影响、迁移方式、破坏性变更必须单独写。
- changelog 面向使用者，写他们感受到的变化，不写内部实现。

## 9 API 文档 / 参数说明（descriptive，strict）

- 参数一列一义：类型、单位、默认值、取值范围、是否必填。
- 写明前置条件、成功结果、失败结果、恢复方式。
- 状态码与错误文案按实际语义翻译，不机械对应单词（Invalid 不一定是"非法"，Unauthorized 不一定是"未授权"）。
- 请求方法、路径、字段名用代码标记，不改写。

## 10 UI 文案（strict）

- 按钮写动作和目标，不重复页面标题。
- 错误提示三段：发生了什么、影响什么、怎么恢复。
- 危险操作写清对象、后果、是否可撤销。
- 空状态区分四种：没有数据、尚未创建、无权限、加载失败。
- 标签极短时句长规则不适用，但一词一义仍适用。

## 11 日志（strict）

- 一行一个事件：时间、组件、动作、对象、结果。
- 不用第一人称，不写"我正在……"。
- 变量用占位符或 JSON 字段，不拼接自然语言句子。
- 级别语义固定：ERROR 表示需要人处理，WARN 表示可自愈，INFO 表示状态变化。

## 不套用的文本

营销文案、品牌口号、叙事文章、观点评论、法律原文、合同条款、需要保留作者语气的段落。这些按项目自己的规范写；本 skill 最多只借用"术语一致"和"指代明确"两条。
